Executive Summary

This assessment evaluated roughly 100 discrete controls drawn from Sections 3.1–3.13 (Hardening Parameters), Section 4 (API Security Best Practices), and Section 5 (Web Service Best Practices) of the guideline. The codebase carries forward a materially strong security baseline — RLS is locked to service_role only, authorization is centralized through a single server-side gate, no SQL-injection or exploitable XSS surface was found, and CSP/HSTS/frame headers are already applied on every response. The team's own internal VAPT pass (July 2026) had already closed 13 of 19 prior findings. This assessment found 28 net-new or still-open gaps against the TATA AIG guideline specifically — most are policy/hardening items (session timeout duration, MFA, audit logging, CI/CD) rather than exploitable bugs. One genuine new access-control defect was identified (H1).

No Multi-Factor Authentication for privileged accounts H3

HighAccepted risk
§3.3 Authentication and Password Management · §4.1 API Authentication
src/routes/auth.tsx · src/lib/auth.functions.ts · src/lib/gate.functions.ts
Status — accepted, by explicit decision (2026-08-06)

User Management (account creation, deletion, and role grants) is not implemented in-app — all of it is done directly against the database, outside any authenticated request path this application serves. There is therefore no in-app privileged action for MFA to protect. The data Admin can see through the app is operational CR/KPI tracking data, not the kind of sensitive record the guideline's "highly sensitive or high value transactional accounts" bar is aimed at. Medium Findings 11

Deployment-management write paths lack per-CR ownership checks M1

MediumResolved
§3.5 Access Control — restrict object references / protected functions to authorized users
src/lib/deployment.functions.ts — createDeploymentSchedule, updateDeploymentSchedule, markDeploymentScheduleCompleted, removeCrFromDeployment, updateDeploymentStage
Resolution (2026-08-06)

All five functions now enforce per-CR/per-application ownership. createDeploymentSchedule and removeCrFromDeployment were already fixed prior to this pass (schedule creation is PMO-only, scoped to the PMO's SPOC applications; CR removal checks the caller is the CR's actual ba/itpm). This pass closed the remaining three: updateDeploymentSchedule and markDeploymentScheduleCompleted are now PMO-only (ITPM/BA can view a schedule but not edit or complete it), and updateDeploymentStage now checks the caller is the CR's ba/itpm for ITPM/BA, or that the CR's application is in the caller's SPOC list for PMO. The internal-trust-pool position previously accepted internally as H6/M6/M7 is superseded by this change, not merely documented as an exception.

Original finding detail
Description

assignCrsToDeployment explicitly verifies an ITPM/BA caller owns the CR(s) they're assigning before proceeding. The five functions above share the same role gate (PMO/ITPM/BA) but perform no per-CR ownership check — any ITPM or BA can create, reschedule, complete, or reassign a deployment schedule for CRs they have no relationship to, by supplying an arbitrary scheduleId/crNumber (obtainable legitimately via listPlannedSchedules, not by guessing).

Context: three of these five functions (markDeploymentScheduleCompleted, updateDeploymentSchedule, and the read path getDeploymentScheduleCrs) were already reviewed internally as H6/M6/M7 and explicitly accepted as risk — the team's stated position is that PMO/ITPM/BA are treated as one trusted internal operations pool, not segmented per-application. This finding is listed for completeness against the external policy (which calls for restricting protected functions to authorized users without carving out an internal-trust exception) and additionally surfaces two functions — removeCrFromDeployment and updateDeploymentStage — that share the same pattern but were not part of the original internal review scope.
Recommendation

Either extend the same ownership filter used in assignCrsToDeployment to all five functions, or formally document the internal-trust-pool decision as a policy exception with CISO sign-off per guideline §7 (Exceptions), explicitly covering the two newly-identified functions.

No general rate limiting/throttling beyond the login form M2

MediumPartially resolved
§3.5 Access Control · §4.4 API Access — "Limit requests (Throttling) to avoid DDoS / brute-force attacks"
src/lib/kpi-engine.ts:253 (recalculateAllKpis) · src/lib/csv-import.ts · src/lib/defect-import.ts · all other server functions
Partially resolved (2026-08-06)

recalculateAllKpis — the specific full-table-scan function this finding calls out — now enforces a 2-minute cooldown between runs, reusing the existing kpi_engine_lock singleton row's started_at instead of a separate rate-limit table. Description

No structured security-event audit logging M3

MediumResolved
§3.7 Error Handling and Logging — log authentication attempts, access-control failures, admin actions
src/integrations/supabase/auth-middleware.ts · src/lib/gate.functions.ts:76-79 · src/lib/auth.functions.ts
Resolution (2026-08-06)

New append-only security_events table, written from a shared logSecurityEvent() helper in src/lib/gate.functions.ts. Wired into the two real denial chokepoints — requireSessionUser (a verified Supabase identity with no/inactive user_management row) and assertHasRoleOrAdmin (authenticated but no role assigned) — plus successful sign-in in auth.functions.ts. Deliberately not wired into every successfully-authorized request (would add a DB write to nearly every page load) or the "no Bearer token yet" branch of requireSessionUser (hit constantly by anonymous session polling — not a meaningful signal on its own). role_change/account-creation events were not added — that admin surface is still DB-only/disabled, per the same reasoning already applied to H3.

Original finding detail
Description

Failed login attempts are logged to a dedicated table (good). However, successful logins, authorization-denied events (requireSessionUser/assertHasRoleOrAdmin throws), input-validation failures, and privileged admin actions (role changes, account creation/deactivation) are not recorded anywhere queryable — only transient console.error on unexpected system errors. This limits incident-response and forensic capability.

Recommendation

Add an append-only security_events table capturing actor, event type (login_success, login_failure, access_denied, role_change, etc.), timestamp, and route — written from the centralized gate functions and any admin-mutation server functions.

Zod present as a dependency but not wired into server-function input validators M4

Resolution (2026-08-06)

File size limit enforced only client-side; bypassable via direct server-function call M5

MediumResolved
§3.12 File Management · §4.5 API Input
src/lib/upload-limits.ts:11-18 — consumed only by client-callable wrappers, not by the .handler() bodies in csv-import.ts, defect-import.ts, test-cases.functions.ts
Resolution (2026-08-06)

New assertPayloadSizeOk() in src/lib/upload-limits.ts, called inside all three handlers (importCrRows, importDefectRows, uploadTestCases) alongside the existing row-count check. Since the original file's bytes never reach the server (parsing is client-side; only the parsed rows array is POSTed), this checks the serialized size of that payload instead — the actual thing a direct/bypassing call would be sending — against the same ceiling. The limit was also lowered from 10 MB to 5 MB per updated policy.

Original finding detail
Description

assertFileSizeOk(file) runs only in the exported client-callable wrapper functions, never inside the actual createServerFn handlers. Because parsing happens in the browser and only the parsed rows array is POSTed, a caller invoking the server-function endpoint directly bypasses the 10MB check entirely. The row-count cap (10,000 rows) does still apply server-side, but there is no server-side cap on aggregate payload/field byte size.

Recommendation

Add a server-side aggregate payload-size guard inside each handler (e.g. total serialized size or max-per-field length), not just a row-count check.

No concurrent-login prevention for the same user ID M9

MediumResolved
§3.4 Session Management — "Do not allow concurrent logins with the same user ID"
src/lib/auth.functions.ts · src/integrations/supabase/client.ts
Resolution (2026-08-06)

New user_management.current_session_id column records the Supabase Auth JWT session_id claim of the most recent login (set in signIn, src/lib/auth.functions.ts). requireSessionUser (src/lib/gate.functions.ts) — the chokepoint every server function already calls — rejects any request whose JWT session_id doesn't match it, logged as an access_denied security event. Logging in from a second device overwrites the column, superseding the first device on its next action (next-request enforcement, not an instant real-time kick — no push channel exists to force a stale tab off mid-session). Basic version implemented, not the polished one: a superseded device sees its next action fail with a generic error toast (existing per-page error handling), not an automatic sign-out + redirect to /auth — that would require wiring a global query-error interceptor, which wasn't built here. One-time effect on rollout: every account signed in before this shipped gets superseded on its next request, since the column starts null — a required, expected cutover, not a bug.

Original finding detail
Description

Nothing in the app or visible Supabase configuration restricts a single account to one active session — the same credentials can be used simultaneously from multiple devices/browsers.

Recommendation

Track active session/refresh-token identifiers per user server-side and revoke prior sessions on new login, if single-session-per-user is a hard business requirement; otherwise document as an accepted exception.

Methodology

Four parallel, independent static-analysis workstreams reviewed: (1) authentication/session/password management and API auth (JWT/OAuth); (2) access control and database security across all 25 Supabase migrations; (3) input validation, output encoding, and file handling; (4) error handling/logging, data protection, communication security, system configuration/headers, and CI/CD.
